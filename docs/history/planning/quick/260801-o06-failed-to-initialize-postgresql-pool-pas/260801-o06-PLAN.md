# Fix: demo postgres auth failure (SQLSTATE 28P01)

## Objective

**Recover the live demo** — the `app` container cannot start because `Failed to initialize
PostgreSQL pool: password authentication failed for user "hourglass"` — **and make the
failure self-diagnosable/recoverable** so it never strands the demo again.

**Purpose:** The demo stack is reachable only via Cloudflare Tunnel + Access; a down `app`
means the prospect demo is dead. The fix is operational, minimal, and reproducible.
**Output:** Running demo + a one-shot `recover-db` compose service + documented recovery paths.

## Root cause (confirmed during planning)

- Named volume `hourglass-demo_pgdata` exists; `deploy/demo/.env` has
  `POSTGRES_PASSWORD` set to a 32-char non-placeholder value, `POSTGRES_USER=hourglass`,
  `POSTGRES_DB=hourglass_demo`.
- Postgres reads `POSTGRES_PASSWORD` **only on first init of an empty data dir**. The
  volume was initialized with an earlier/different password, so the stored password no
  longer matches `.env`. The app's `DATABASE_URL` (composed from the same env vars) is
  rejected with `FATAL: password authentication failed` (SQLSTATE 28P01) and the app
  FATAL-exits at startup.

  <name>Task 1: Recover the live demo by realigning the stored postgres password with .env</name>
  <files>no files — pure operational remediation on the running compose stack</files>
  <action>
    Repairs the running stack in place, preserving demo data (no volume wipe unless the
    ALTER path is impossible). Never print POSTGRES_PASSWORD to logs, shell history, or
    your own output — read it from deploy/demo/.env inside a script and pipe SQL via stdin.

    1. Confirm the failure and stack state:
       `docker compose -f deploy/demo/docker-compose.yml ps` (app expected restarting/Up-but-crash-looping)
       `docker compose -f deploy/demo/docker-compose.yml logs app --tail=30 | grep -i "password authentication failed"` (expected: present)

    2. Realign the password in place. The postgres:17-alpine image trusts local unix-socket
       connections by default, so `docker compose exec` psql needs no old password:
       ```bash
       ENV_FILE=deploy/demo/.env
       PW=$(grep -E '^POSTGRES_PASSWORD=' "$ENV_FILE" | head -1 | cut -d= -f2-)
       USER=$(grep -E '^POSTGRES_USER=' "$ENV_FILE" | head -1 | cut -d= -f2-)
       ESC=$(printf '%s' "$PW" | sed "s/'/''/g")   # psql single-quote escaping
       printf "ALTER USER \"%s\" WITH PASSWORD '%s';\n" "$USER" "$ESC" | \
         docker compose -f deploy/demo/docker-compose.yml exec -T postgres \
         psql -U "$USER" -d postgres -v ON_ERROR_STOP=1
       ```
       (`-T` disables TTY allocation so stdin piping works; ALTER USER is cluster-wide, so
       connecting to the `postgres` maintenance DB is correct regardless of POSTGRES_DB.)

    3. Prove the app's exact DATABASE_URL now authenticates:
       `docker compose -f deploy/demo/docker-compose.yml run --rm migrate`
       (must exit 0 without a SASL/28P01 error; `migrate -all` is idempotent).
       Then restart the app and confirm it stabilizes:
       `docker compose -f deploy/demo/docker-compose.yml up -d app` and
       `docker compose -f deploy/demo/docker-compose.yml ps app` → Up, not restarting.
       `docker compose -f deploy/demo/docker-compose.yml logs app --tail=30` → no
       "failed to initialize PostgreSQL pool" / "password authentication failed".

    4. Re-seed demo data (idempotent, restores fresh demo state):
       `docker compose -f deploy/demo/docker-compose.yml run --rm seed`

    5. Fallback (only if the ALTER-via-socket path cannot run — e.g. exec/psql errors that
       cannot be resolved in a few minutes): nuclear reset, which wipes the demo DB:
       `docker compose -f deploy/demo/docker-compose.yml down -v` then
       `docker compose -f deploy/demo/docker-compose.yml up -d` then
       `docker compose -f deploy/demo/docker-compose.yml run --rm migrate` then
       `docker compose -f deploy/demo/docker-compose.yml run --rm seed`.
       Postgres re-initializes the empty volume with the current .env password.
       Prefer the ALTER path — the nightly seed makes data loss cheap, but avoid it anyway.
  </action>

    1. deploy/demo/docker-compose.yml — add a `recover-db` one-shot service mirroring the
       existing `seed` service's style (profiles: ["ops"], image postgres:17-alpine,
       depends_on postgres service_healthy, restart "no"). It ALTERs the superuser password
       to the current .env value using psql's `:'pw'` variable interpolation (safe quoting —
       do NOT inline the password into the -c string):
       ```yaml
       # One-shot: realign postgres superuser password with .env when the pgdata volume
       # already exists (postgres only reads POSTGRES_PASSWORD on first init of an empty
       # data dir). Run: docker compose run --rm recover-db  (idempotent)
       recover-db:
         profiles: ["ops"]
         image: postgres:17-alpine
         entrypoint: ["/bin/sh", "-c"]
         command:
           - "psql \"postgres://${POSTGRES_USER}:${POSTGRES_PASSWORD}@postgres:5432/postgres?sslmode=disable\" -v ON_ERROR_STOP=1 -v pw='${POSTGRES_PASSWORD}' -c \"ALTER USER ${POSTGRES_USER} WITH PASSWORD :'pw';\""
         depends_on:
           postgres:
             condition: service_healthy
         restart: "no"
       ```
       Note: double-quoted YAML scalar keeps single quotes literal; compose interpolates
       `${POSTGRES_USER}`/`${POSTGRES_PASSWORD}` from .env. Target the `postgres` maintenance
