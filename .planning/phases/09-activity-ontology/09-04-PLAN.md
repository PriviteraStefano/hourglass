# Plan 09-04 — Service Layer Rewrite

Rewrites the approval-routing logic per ADR-BE-014 and creates the new Activity service. The core change: routing resolution moves from pinned FKs to the activity chain (R-1), with the unit-manager fallback for personal activities (R-2) and the D-11 skip extended to delegates (R-3).

Depends on Plans 01 + 03 (schema + repositories must exist). Runs in parallel with Plan 02.

<type>execute</type>

<action>

- `internal/core/services/activity/activity.go`: `ActivityService` struct with port dependencies (ActivityRepository, ContractRepository, UnitRepository for visibility).
- CRUD methods: Create, GetByID, Update, Delete, List (by org, by contract, by parent), ListChildren.
- Create: validates kind exists in the org's `activity_kinds` catalog (D-2), validates parent exists and belongs to the same org, validates contract exists if provided. Personal/internal activities (no contract) are first-class — no validation requiring commercial context.

- Delete `internal/core/services/project/project.go` — the activity service replaces it entirely.

<task id="2">
<type>execute</type>

<action>
Rewrite the time-entry service's approval routing.

- `internal/core/services/time_entry/time_entry.go`: `Submit` and `Approve` methods rewritten per BE-014.
- **R-1 chain**: on Submit, resolve the entry's `activity_id` → anchored WG (`working_groups.activity_id`) → WG manager + delegates. This is the manager stage.
- **R-2 fallback**: if the activity has no anchored WG **and** no `contract_id` (personal activity per D-8), the manager stage is the submitter's unit manager — resolved via `unit_memberships.role = 'manager'` on the entry's `unit_id`, walking the unit tree upward if the direct unit has no manager.
- **R-2 enforcement**: if the activity has a `contract_id` (commercial work) but **no anchored WG**, reject submission with `ErrActivityNotLoggable` (409) — commercial activities must anchor a WG before accepting entries.
- **R-3 (D-11 skip)**: if the entry's WG manager **or any delegate** is the entry owner, `submitted` transitions directly to `pending_finance`. The check is role-based (is the owner in the approver set?), not identity-based (owner != manager) — the distinction must be explicit in code.
- **R-4 visibility**: `List` and `ListPending` already gate on unit subtree via the repository (Plan 03) — verify the service passes the correct `unit_id` scope and doesn't add a second filter.
- Finance stage unchanged: org-role `finance` approves from `pending_finance`.
</action>

- Submit on a personal activity (no contract, no WG) routes to the submitter's unit manager
