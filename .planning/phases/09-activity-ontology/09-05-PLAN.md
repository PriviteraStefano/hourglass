# Plan 09-05 — HTTP Handlers + Route Wiring

Collapses the project/subproject HTTP surface into a single activity handler, updates entry handlers for the new FK shape, and rewires the router. After this plan the backend API is fully activity-shaped — the frontend rename (Phase 10) becomes a pure rename against stable endpoints.

Depends on Plans 01 + 03 + 04 (schema, repositories, services must all exist).

<task id="1">
<type>execute</type>

<action>
Create the activity handler and delete the old project/subproject handlers.

- `internal/adapters/primary/http/activity_handler.go`: thin adapter per ADR-BE-002 — parses requests, calls ActivityService, maps responses and sentinel errors to HTTP codes per ADR-BE-001.
- Endpoints:
  - `GET /api/activities` — list by org (with optional `parent_id`, `contract_id`, `kind` filters)
  - `POST /api/activities` — create
  - `GET /api/activities/:id` — detail (includes ancestry chain + derived commercial context)
  - `PUT /api/activities/:id` — update
  - `DELETE /api/activities/:id` — delete (409 on has-children / has-active-entries)
  - `GET /api/activities/:id/children` — list direct children
  - `GET /api/activity-kinds` — list the org's kind catalog
- Response DTO for detail includes: the activity itself + `ancestry` (ordered parent chain) + `commercial_context` (derived contract_id + customer_id, or null) + `billable` (resolved via inheritance walk).
- Delete `project_handler.go` and `subproject_handler.go`.
</action>

<read_first>
- `internal/adapters/primary/http/project_handler.go` + `subproject_handler.go` (current handler patterns to preserve)
- `internal/core/services/activity/activity.go` (from Plan 04 — the service being adapted)
- `hourglass-vault/decisions/backend/ADR-BE-001 — Error Handling Sentinel Errors.md` (error → HTTP mapping)
- `hourglass-vault/decisions/backend/ADR-BE-002 — Hexagonal Wiring.md` (handler pattern)
</read_first>

<acceptance_criteria>
- Activity handler exposes all seven endpoints; project/subproject handlers are deleted
- Detail response includes ancestry + derived commercial context + resolved billability
- Sentinel errors map to correct HTTP codes (404 not-found, 409 has-children / has-entries / not-loggable, 403 forbidden)
- Handler integration tests pass against testcontainers
</acceptance_criteria>
</task>

<task id="2">
<type>execute</type>

<action>
Update the time-entry and expense handlers for the new FK shape.

- `time_entry_handler.go`: request DTOs replace `project_id`, `subproject_id`, `wg_id` with `activity_id` (required string, parsed to uuid). Response DTOs include `activity_id` + `activity_name` (+ optionally `activity_kind`). Validation: `activity_id` required, must parse as UUID.
- `expense_handler.go`: same treatment — `project_id`, `customer_id` → `activity_id` (required).
- Both handlers: the submit endpoint's error mapping must handle `ErrActivityNotLoggable` → 409 with a clear message ("this activity requires a working group before entries can be logged").
- List endpoints: filter params `project_id` / `subproject_id` → `activity_id` (single filter, matches any depth — the repository resolves the subtree).
</action>

<read_first>
- `internal/adapters/primary/http/time_entry_handler.go` + `expense_handler.go` (current DTOs and validation)
- `internal/core/services/time_entry/time_entry.go` + `expense/expense.go` (from Plan 04 — new signatures)
- `internal/core/domain/time_entry.go` + `expense.go` (from Plan 03 — new domain shapes)
</read_first>

<acceptance_criteria>
- No handler DTO references `project_id`, `subproject_id`, `wg_id`, or `customer_id` (on entries)
- `activity_id` is required on create/update for both entry types
- Submit returns 409 with clear message when the activity is not loggable
- List filters accept `activity_id` and return entries for that activity and its descendants
- Handler integration tests pass (create, submit, approve, list with filters)
</acceptance_criteria>
</task>

</action>
