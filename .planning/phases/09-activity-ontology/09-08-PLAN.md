# Plan 09-08 — Gap fix: cycle prevention on activities.parent_id (GAP 3)

<objective>
Close VERIFICATION GAP 3: the SPEC in-scope item "Cycle prevention on `activities.parent_id` (path check on insert/update)" was never implemented — Create validates parent existence + same-org only, and Update validates neither parent nor cycles, so the recursive CTEs could loop. The fix adds a service-layer ancestor-path check: walk `GetAncestry` of the proposed parent and reject when the chain contains the activity's own id, via a new `ErrActivityCycle` sentinel (ADR-BE-001 pattern). Update also gains Create's parent exists + same-org validation (the latent gap the verifier flagged). The repository stays permissive — the service is the single enforcement point all API traffic passes through.

Purpose: Implement the locked SPEC in-scope item and make the corresponding truth green.
Output: Domain sentinel, service enforcement on Create+Update, mock ancestry derivation, unit tests, handler 400 mapping.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-08-01 | Tampering | activities.parent_id via API | mitigate | Enforcement is server-side in the service (Create + Update share `validateParent` walking repo.GetAncestry); client-supplied parent is never trusted; a cycle attempt returns ErrActivityCycle → HTTP 400, not a silent write |
| T-09-08-02 | Tampering | Update parent same-org bypass | mitigate | Update now mirrors Create's Get + OrgID check before delegating to the repo (latent gap closed) — cross-org parent → ErrInvalidRequest → 400 |

| T-09-08-04 | Tampering | cycle via direct repo use | accept | The service is the only call path the API exposes; repo stays permissive by design (single enforcement point documented in the service comment) |

No high-severity threats.
