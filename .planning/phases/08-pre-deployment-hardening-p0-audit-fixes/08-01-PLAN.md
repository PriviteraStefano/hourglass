<task id="2">
<type>execute</type>

<action>
Implement refresh-token rotation with reuse detection (P0-5). Every successful `/auth/refresh` call: (a) issues a brand-new refresh token, (b) revokes the presented token, (c) if an already-rotated/revoked token is presented, revokes the entire token family.

- Migration `011_refresh_token_rotation`: extend the refresh-token persistence (tokens table) with `family_id UUID NOT NULL`, `rotated_at TIMESTAMPTZ NULL`, `revoked_at TIMESTAMPTZ NULL`; index on `family_id`
- `TokenService.IssuePair(userID, …)` → persists a new row with a fresh `family_id` (new family on login/register)
- `TokenService.Rotate(presentedToken)` → validates → in one transaction: mark presented row `rotated_at=now()`, insert successor row with the same `family_id`, return new pair; if presented row already has `rotated_at` or `revoked_at` set → set `revoked_at` on ALL rows of that family, return an `ErrTokenReuse`-style sentinel error
- Update `authHandler.Refresh` to call `Rotate` and set the new `refresh_token` cookie (7d TTL unchanged, mechanism per ADR-FE-013 unchanged)
- On `ErrTokenReuse` → 401 + clear both cookies
- Logout revokes the presented token's row (unchanged behavior, now via `revoked_at`)
</action>

<read_first>
- `internal/core/services/auth/token_service.go` (current issue/validate/refresh logic)
- `internal/core/domain/auth/` (token domain types)
- `internal/adapters/primary/http/auth.go` (Refresh handler + cookie setting, `auth_token`/`refresh_token` cookie names)
- `migrations/008_verification_tokens.up.sql` (token-table conventions)
- Audit note §4 T5 (rotation rationale) and T9 (refresh endpoint posture)
</read_first>

<acceptance_criteria>
- `migrations/011_refresh_token_rotation.up.sql` adds `family_id`, `rotated_at`, `revoked_at` and applies/rolls back cleanly
- Happy path: login → refresh twice in sequence → each refresh returns a *different* refresh token value; the cookie is updated each time
- Old-token rejection: reusing the first refresh token after one rotation returns 401 and clears cookies
- Reuse detection: reusing any rotated token revokes the family — a subsequent refresh with the *latest* valid token of that family then fails
- `ErrTokenReuse` (or equivalent sentinel) exists and is asserted in tests
- `go test ./internal/core/services/auth/...` passes, including new rotation + reuse-detection cases
- Existing auth handler tests (`internal/adapters/primary/http/auth_test.go`) still pass
</acceptance_criteria>
</task>

<task id="3">
<type>execute</type>

<action>
Remove the password-reset code from the API response (P0-6) and increase code entropy.

- `passwordResetHandler.Request`: response body becomes a generic success message (`{"message":"if the account exists, a reset code has been sent"}`) returned regardless of whether the email exists (no user enumeration)
- The reset code is no longer serialized in any response field (check the response struct and any `code`/`reset_code` JSON tags)
- Increase the code from 3 digits to 8 digits (crypto/rand, numeric) — trivial since the endpoint is being touched
- Delivery channel: log the code server-side in dev (stdout log line) so dev flows still work; production mailer is out of scope (deployment config)
- Update the verify endpoint only if its contract references the code length
</action>

<read_first>
- `internal/adapters/primary/http/password_reset.go` (Request + Verify handlers, response structs)
- `internal/core/services/auth/` (reset-code generation + storage)
- Audit §4 T8 (exposure + 3-digit entropy rationale)
- `web/src/routes/_auth/password-reset/` (frontend flow — must not depend on a response-body code)
</read_first>

<acceptance_criteria>

</task>

<task id="4">
<type>execute</type>

<action>
Add request-string length caps across public-facing handlers (audit S3). Domain value objects validate format but not max length — add explicit caps at the handler boundary before service calls.

- Introduce a small shared helper (e.g. `internal/adapters/primary/http/validate.go`) with per-field limits: email 320, name 200, description/notes 4000, address 500, VAT 50, phone 50, password 128, generic short strings 500
- Apply in: auth (register, login, profile update), password_reset, customer, contract, project, time_entry, expense, unit, working_group handlers — on every string field decoded from request bodies
- Violation → 400 with a field-level error message (`field exceeds maximum length of N`)
- No changes to domain value objects (caps live at the adapter boundary per hexagonal layering)
</action>
