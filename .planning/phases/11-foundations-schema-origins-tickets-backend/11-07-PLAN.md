<objective>
Close code-review CR-01 for the ticket state machine and dismissal guard (VERIFICATION.md gaps 1+2, root cause): every matrix/guard decision is re-validated INSIDE the mutator transaction under a `FOR UPDATE` ticket row lock, mirroring the already-correct triage pattern (Pitfall 7, ADR-BE-016). After this plan, TICK-02's lifecycle and TICK-04's dismissal guard (T-11-07) hold under concurrency: a dismissed ticket cannot be resurrected to 'planned', 'planned → dismissed' is impossible, and dismissal cannot commit with `dismissed_hours=0` while committed logged hours exist at check time.

Purpose: The two failed must-have truths (9/11 score) share one root cause — the domain checks run at pool level before the mutator tx, leaving a check-then-act window across the tx boundary. The fix lands in the repository layer only (no port signature changes, no mock churn), following the exact pattern Triage already proves: in-tx `SELECT ... FOR UPDATE`, re-validate, then write.

Output: Hardened `UpdateState` / `Dismiss` / `Triage` in `ticket_repository.go`, a concurrency test battery that is RED on the current code and GREEN after the fix, and updated service doc comments reflecting the fast-fail-vs-authoritative layering.
</objective>
