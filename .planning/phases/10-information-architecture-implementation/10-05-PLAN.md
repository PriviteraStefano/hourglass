| T-10-05-3: Employee-with-WG-stage gets 403 because `ListPending` handler hard-gates on org role manager/finance | high | Task 10-05-01 verifies service semantics in code; if the handler gate excludes WG-stage employees, fix the handler to admit WG manager/delegate (the service already re-resolves the approver set) — backend test updated accordingly |
| T-10-05-4: Reject without reason | medium | Existing `approval-buttons.tsx` pattern requires reason input (alert-dialog); reuse unchanged |

</threat_model>

## Context

ADR-P-011 D-3: Approvals leave Track and become the **Review** group — one page, two stage-filtered queues (manager stage, finance stage per BE-014 two-stage chain). Rendered only for users holding an approval stage; HR never. Backend: `GET /time-entries/pending` + `GET /expenses/pending` (both currently 403 unless org role ∈ {manager, finance} — see T-10-05-3), `POST /{id}/approve`, `POST /{id}/reject` (reason required).

UI-SPEC locks: Header = title "Approvals" + Manager/Finance `Tabs` (render only the user's stage(s)) + queue filters; first pending row + Approve/Reject pair is the focal point; actions are the only accent below the tab bar; Reject in destructive; rows `py-3` (single ladder exception); StatusBadge unchanged; empty state "Queue is clear" per stage ("There are no {stage} approvals waiting. Submitted entries will appear here for review."); reject confirmation copy per Copywriting Contract.
