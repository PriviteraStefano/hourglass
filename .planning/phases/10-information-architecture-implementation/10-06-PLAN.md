# Plan 10-06 — Working Groups surface

<threat_model>

| Threat | Severity | Mitigation |
|--------|----------|------------|
| T-10-06-1: Member management mutates another org's WG | high | Backend org-scopes all WG endpoints (middleware.GetOrganizationID) — client never sends org ids; e2e asserts org isolation is not client-enforced |
| T-10-06-2: Manager/delegate pickers accept non-org users | medium | Picker options sourced from org members endpoint (`GET /organizations/members` or units members — read_first verifies which exists client-side); backend validates membership |
| T-10-06-3: WG delete orphans approvals chain | medium | Backend returns 409-style guards where applicable; client surfaces backend error verbatim via toast (no client-side cascade logic invented) |

</threat_model>

## Context

ADR-P-011 D-4: Working Groups get a top-level surface under **Work** — execution structure needs its own home (assignment is the consumption point of availability/validity warnings later; those land with P-008, NOT in this phase). The WG API is fully live since Phase 9: `GET/POST /working-groups`, `GET/PUT/DELETE /working-groups/{id}`, `GET/POST/DELETE /working-groups/{id}/members` (payload includes `activity_id`, `manager_id`, `delegate_ids[]`, member `role`).

UI-SPEC locks: Header = title "Working Groups" + search bar + "New working group" CTA right-aligned (single accent element); WG cards in muted/card surfaces; empty state heading "No working groups yet" + body "Working groups assign people to activities. Create one to start staffing work." + CTA "New working group"; v0.1 scope = list + create/edit + members (no availability warnings).
