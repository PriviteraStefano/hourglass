## 2. Gaps & Decisions the Plan Must Resolve

### 2.1 ⚠ Approval-stage visibility gap (the one real design decision)

The UI-SPEC mandates: render only the tab(s) matching the user's approval stage — Manager tab for WG managers/delegates, Finance tab for org-role finance. But:

* `GET /time-entries/pending` and `/expenses/pending` are gated on **org role** (`manager`/`finance` via `middleware.GetRole`) and the service resolves the manager-stage approver set = WG `ManagerID` + `DelegateIDs` server-side (Phase 9 09-04).
* The WG API exposes `manager_id` + `delegate_ids` on every WG payload, so the client **can** compute "user is a WG manager/delegate" from `GET /working-groups` + `auth/me` — no new endpoint strictly required.
* An org-role `employee` who manages a WG currently gets **403** from `/pending` if the org role isn't manager/finance. Whether Phase 9's `ListPending` service admits WG-stage approvers with org-role employee needs verification at plan time (read `TimeEntryService.ListPending` before finalizing the Approvals plan). **Plan fallback:** Approvals page renders for users who are (org-role manager/finance) ∨ (WG manager/delegate); tabs are scoped client-side; backend 403s are tolerated as "queue is clear" only if the service confirms org-role gating — otherwise surface the gap as a small backend task.

**Recommendation for planner:** treat "client derives stage visibility from `auth/me` + WG list" as the v0.1 mechanism (ADR-P-011 D-5: sidebar hiding is UX scoping, backend stays authoritative), and include one `read_first` verification task on `ListPending` semantics.

### 2.2 Route rename mechanics

* Rename directory `routes/_authenticated/projects/` → `activities/`; route paths update via file-based generation.
* Vocabulary sweep inside the moved components: "Projects" → "Activities", "New project" → "New activity", CTA/copy per Copywriting Contract. `project-list.tsx`, `project-detail.tsx`, `create-project-dialog.tsx`, `edit-project-dialog.tsx` rename to `activity-*` (component renames are optional but recommended for grep-ability; imports are path-based).
* API layer `web/src/api/projects.ts` → `activities.ts`, endpoints `/projects*` → `/activities*` (+ `/activity-kinds`), types `Project`/`Subproject` → `Activity` (frontend type reshape to match Phase 9 DTOs: `kind`, `parent_id`, `activity_name`/`activity_kind` on entries).
* **No redirect shim:** pre-deploy, no URLs to preserve (ADR-P-011 D-6). `/projects` simply stops existing.
* Entry forms (time-entries/expenses) reference project/subproject pickers — these consume `activity_id`; check `entry-detail.tsx` / expense-detail and the create-entry flows for project-picker components that need activity pickers (cascading parent/child via `GET /activities` + `/{id}/children`).

### 2.3 Today page composition (ADR-P-004 + UI-SPEC)

Sections, top-down, no side-by-side competing cards:

1. **"Waiting on you"** — approver's pending approvals; renders **only** if user holds an approval stage (same visibility rule as Review group); CTA "Review now" → `/approvals`
2. **"Your week"** — own draft/submitted/rejected entries this week (time entries; expenses if cheap — same query pattern); CTA "Log time" → `/time-entries`
3. **Empty states** (locked copy): "You're all caught up" / "Welcome to Hourglass" (new user)

Data sources: `GET /time-entries?month=…` already exists (calendar uses it); a week-scoped filter can reuse the same endpoint client-side (filter by `entry_date` in the current ISO week) — **no new endpoint needed**. Read-only composition: no new state, no charts/KPIs, never blank.

Greeting/title is Display 28px in the shell `Header` with right-aligned primary CTA ("Review now" for approvers, else "Log time").

### 2.4 Approvals page composition

* Route `/approvals`, shell `Header`: title + Manager/Finance `Tabs` + queue filters; render tabs matching user's stage(s) only.
* Queue rows: pending time entries + expenses (two queries, merged client-side or a `kind` column), `StatusBadge` unchanged, `ApprovalButtons` for the action pair, reject → `alert-dialog` with reason input (existing pattern), destructive color only on Reject.
* Row density exception: `py-3` permitted (matches entries-table).
* Empty state: "Queue is clear" per stage.
* Role gating: page + Review group hidden from HR and employees without a stage; direct URL access by non-approvers → the backend 403s; the page should render a polite empty/error state rather than crash (errorComponent convention).

### 2.5 Working Groups page composition

* Route `/working-groups`, shell `Header`: title + search + "New working group" CTA.
* Card grid (muted/card surfaces, single accent = header CTA). WG card shows name, activity link, manager, member count.
* CRUD via the live WG API: Create/Update dialogs (name, activity picker, manager picker, delegates), member management (AddMember/RemoveMember) on a detail view or expandable card — **scope decision for planner:** v0.1 surface is list + create/edit + members; no availability warnings yet (P-008 surfaces follow schema).
* Empty state: "No working groups yet" + CTA.

### 2.6 Role-scoped sidebar (ADR-P-011 D-5 matrix)

v0.1 implementable subset (client-side, from `auth/me.membership.role` + WG-derived stage):

| Group | employee | manager | finance | hr |
|-------|----------|---------|---------|----|
| Today / Track | ✓ | ✓ | ✓ | ✓ |
| Work | ✓ (read surfaces exist; form affordances stay — backend enforces) | ✓ | ✓ | ✓ |
| People | ✓ | ✓ | ✓ | ✓ |
| Economics | **hidden** | ✓ | ✓ | ✓ |
| Review | hidden unless WG manager/delegate | ✓ (Manager tab) | ✓ (Finance tab) | **never** |
| Reports | ✓ | ✓ | ✓ | ✓ |
| Admin | hidden | hidden | hidden | hidden (org admin — no admin role exists yet; keep group rendered-but-disabled as today, or hide uniformly — planner's call, recommend: render for all-but-hidden logic minimal, keep disabled Settings visible as today to avoid dead config) |

Note: `Role` type in `web/src/types/models.ts` is `"employee" | "manager" | "finance" | "customer"` — **`hr` is missing**. Phase 9 migration 012 added the `hr` role to the DB CHECK. The frontend union must be extended (one-line type change) or hr users will fail zod/type narrowing.

### 2.7 E2E fallout (must be in the plan)

* `auth.spec.ts:64,81` — asserts `/` → `/time-entries`; must assert Today instead.
* `projects.spec.ts` — full rename to `activities.spec.ts` (paths + copy + API globs).
* `error-boundary.spec.ts` — anchored on time-entries API globs; unaffected by rename but landing-route change may alter its navigation setup (verify).
* Seeding: WG/approvals e2e need WG rows + users with stages; follow the Phase 8 convention (shared helpers module, API login + cookie injection, `RATE_LIMIT`/`ANONYMOUS_RATE_LIMIT` raised).

### 2.8 Wrap-only shell migration (carried-over pages)

Pages currently rendering bare into `SidebarInset`: time-entries, expenses, exports, contracts (+$id), customers (+$id). Each gets `<Header>{title + existing CTA/filters}</Header><Body>{existing content}</Body>` — **no re-layout, no control redesign** (UI-SPEC lock 7). Route `errorComponent`/`pendingComponent` render inside `Body` so the shell survives load/error states (Phase 8 leaf-level boundary convention stays).

## 5. Risks / Landmines

* **`routeTree.gen.ts` conflicts** — never hand-edit; let the plugin regenerate; commit the regenerated file.
* **403-vs-empty ambiguity on Approvals** — distinguish "no pending" from "forbidden" via the WG/org-role derivation, not by swallowing 403s.
* **Vocabulary residue** — grep for `project`/`subproject` in `web/src` after rename; the backend payloads no longer contain those words, so type mismatches will surface at typecheck (TS 7 via oxlint type-aware).
* **Today "never blank"** — both empty states must be reachable; test the new-user state (no entries at all) separately from caught-up.
* **Sidebar active-state** — `useMatchRoute({ to })` exactness on `/` (Today) vs prefix matching; Today must not stay active on every route.
* **Playwright login rate limit** — reuse Phase 8 cookie-injection helper; raise `RATE_LIMIT`/`ANONYMOUS_RATE_LIMIT` for full-suite runs.
